what hosting actually is

A file nobody can reach isn't a website yet

You built something. It works when you open it on your own phone. But nobody else can see it, because it only exists on your device. Hosting is the step that puts a copy of your file on a computer that is always on and always reachable, and hands you a web address that points at it.

That's the whole trick. A host is just a computer that stays awake so your file has an address. When someone types that address, the host sends them a copy of your file. GitHub Pages is one of these hosts, and it's free.

You already did this. This course lives on GitHub Pages. Everything below is the thing you fought with to get the mascots to show up, taken apart slowly.

the repo

The repo is the box you put files in

A repository (repo) is a folder that lives on GitHub. You put your files in it. GitHub Pages watches one repo and serves whatever is inside it to the web. Add a file, it appears at the address. Delete a file, it's gone from the address.

Try it. Add a couple of files to this pretend repo, then hit Publish and see what address each one gets.

The address is built from the name

A file called about.html in the repo root becomes …/about.html. The name you give the file IS part of the address. Rename the file, the address changes, and old links break.

the front door

index.html is the front door

When someone visits your address with no file name on the end, like …/demo/, the host looks for one special file: index.html. That's the front door. If it's there, the visitor sees it. If it's missing, they get an error instead of your site.

This is why the course hub is named index.html and not hub.html. Type the bare address, the host serves index.html automatically.

root vs folder

Where a file sits decides how you point at it

This is the exact thing that broke your mascots. A file's address depends on where it lives in the repo. Two choices:

Flat (root): the image sits right next to index.html. Your code points at it by bare name: thumb-git.png.

In a folder: the image sits inside a folder called img. Now the same code has to say img/thumb-git.png, with the folder name and a slash in front.

If the code and the file disagree, the browser asks for an address that has nothing at it, and the image shows broken. Line them up below.

The zip trap you hit

GitHub's web uploader does not unpack a zip. It just stores the zip as one file. To get a folder up, either upload the loose files into a folder, or go flat and keep everything in the root. Flat is the simplest on a phone.

the phone trap

Opening from Downloads is not the same as opening from the web

Here's the one that fools everyone on a phone. When you open your HTML file straight from your Downloads folder, the address bar shows something like content:// or file://. That is not the web. It's your phone handing you the raw file off local storage.

Things that quietly break in that mode: saved progress vanishes between opens, images by relative name may not load, and anything that needs a real web address (like a service worker) just won't run. Then you upload it, open the real https:// address, and suddenly it all works. The file was never broken. The way you opened it was.

🔒
The fix is always the same

If something works in Downloads but not once uploaded, or the reverse, check the address bar first. If it doesn't start with https://, you're not testing the real thing. Open the Pages URL instead.
