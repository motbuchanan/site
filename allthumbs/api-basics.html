what an api is

An API is an order window on someone else's computer

Chapter 2 showed you a browser asking a server for a page: you type an address, the server sends back HTML, the browser paints it. An API call is the same move with one difference: instead of asking for a page to look at, your code asks for data to use. A weather number. A list of games. A save confirmation. The server answers with plain data, no page around it, and your app decides what to do with it.

Think of a restaurant with a walk-up window. You do not go in the kitchen. You hand over an order in the format the window expects, you get a ticket number, and a minute later something comes back. The window is the API: a fixed, public way to ask the kitchen for things without touching the kitchen. API stands for Application Programming Interface, which is a stiff way of saying "the agreed-upon order window."

You have been using these the whole time. Every Firebase save, every weather slide on the office screens, every time an app checks something on another server: an order went through a window and an answer came back.

the shape

Every call has the same four parts

A verb (what kind of order: GET to fetch, POST to send something new, PUT to replace, DELETE to remove). A URL (which window, and which thing at that window). Sometimes a body (the actual order details, for POST and PUT). And then the server's response: a status code plus the data.

GET is reading, POST is writing

The verb tells the window what kind of visit this is. GET means "just show me," it changes nothing and you can repeat it safely. POST means "here is something new, keep it." That is why a page refresh after a POST can warn you about resubmitting: the browser knows a second POST might make a second order.

status codes

The first thing back is a number that tells you how it went

Before any data, the server sends a three-digit status code. You already know one of them. The first digit is the whole story:

2xx  worked. 200 OK, 201 created.

4xx  your order was wrong. 404 nothing at that address, 401 you are not signed in, 403 signed in but not allowed, 429 you are asking too fast.

5xx  the kitchen is broken. 500 the server crashed on your order, 503 it is down. Not your fault; wait and retry.

The habit that saves you hours: read the number before you read anything else. A 4xx means fix your request. A 5xx means fix nothing, wait. A 2xx with weird data means the call worked and the problem is in how you handled the answer.

The one that looks like your bug but is not

A 503 or a 500 at 2am is the service having a bad night. The weather screens going blank at the offices is almost always this: the weather window is down, not your slide code. Build the slide to show the last good answer when the new one fails, and the blank disappears.

reading the answer

The data comes back as JSON, which is just labeled boxes

APIs almost always answer in JSON: text shaped like {"label": value}. Curly braces hold a set of labeled things, square brackets hold a list, quotes mark text, bare numbers are numbers. It looks scary in a wall but it is only ever those four shapes nested.

Your code pulls out what it needs by following the labels: answer.temp gets the temperature, answer.scores[0].name gets the first player's name. Tap a label below and watch the path light up.

keys and limits

Most windows want to know who is ordering

A public window (a free weather feed) takes anyone's order. Most others hand you an API key: a long string that says "this order is from Mot's app." You send it with every call. It is how the service counts your usage, bills you if there is a bill, and shuts you off if you misbehave.

Two things the key teaches you. First, a key in a page is a key anyone can read. View-source shows it. For a free, read-only weather key that is fine. For a key that can spend money or write data, it belongs on a server you control, never in the HTML. Second, windows have rate limits: ask 1000 times a minute and you get 429 until you slow down. The weather screens poll every few minutes, not every second, for exactly this reason.

This connects straight back to Chapter 8. The Firebase config in your page is the "which window" part. The security rules on the cabinet are the "who is allowed" part. Same split: address is public, permission is enforced server-side.
