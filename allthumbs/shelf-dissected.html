adding a game

A new game has to be registered in four places, or it breaks quietly

This is the single most important thing in the chapter, and it is the thing that bit you in July. A game is not "on the shelf" when its HTML file is uploaded. It is on the shelf when four separate lists know about it. Miss one and nothing errors. The shelf just quietly does the wrong thing, sometimes weeks later.

Pretend you just finished puffkart.html. Tick what you remembered to do, then read the verdict.

Why four lists and not one

Each list is read by a different part of the system at a different moment: the hub when it draws tiles, the service worker when it seeds offline copies, the sync layer when it resets the cabinet, the badge system when it hands out achievements. None of them read each other. That is normal in software and it is exactly why a checklist beats memory. Chapter 6 taught you commits; this is why a commit should touch all four files at once.

the service worker

Why the shelf plays with no signal, and why the badge number matters

sw.js is a small script the browser installs beside your site and keeps running between visits (Chapter 7 mentioned it as the thing that will not run from content://). The shelf's worker is network-first: when you are online every request goes to the real server, so an upload shows up on a plain refresh. As responses fly past, it quietly saves copies. Offline, it serves those copies, so Garrett can play in the car.

It also precaches a list of core files on install, 135 of them today, so the first offline visit already has the hub, the shared scripts, and the main games. That list lives in a constant called CORE, and the cache itself is named gameshelf-v70.

That name is your deploy ritual. Bumping it to v71 tells every device "throw out the old copies, seed fresh ones." Forget the bump after changing the precache list and devices keep serving stale files. This is the same stale-cache lesson from Chapter 2 and the badge rule from this course, running inside your own app.

From v1 to v70 in four months

The cache name has been bumped roughly 70 times since June 12. Each bump is a real deploy you made from a phone. The timeline section has the full run.

the cabinet

gamenight.js is the cabinet door, and here is the bug that hid in it

gamenight.js (132 KB, the biggest shared script) holds the Firestore config, the sign-in, and the sync. Chapter 8 called a database "a shared cabinet." Here it is for real: every finished game writes a record under a key like chess_games or c4_games, and a collection-wide live listener (onSnapshot, Chapter 8's "subscribe") pushes every change to every device.

There is a list called GAME_KEYS naming every record key, 47 today. It is the fourth registration from the checklist above, and in July eight arcade games were missing from it. Day to day, nothing looked wrong. Then someone did a household reset:

The v34 bug, step by step. Reset walks GAME_KEYS and deletes each key's records from the cabinet. The eight unlisted keys were skipped, so their records stayed alive in Firestore. The live listener saw the collection change, read the surviving records, and pushed them back down onto every device. The reset undid itself. No error, no crash, just scores that would not go away. The fix was one edit: add the eight keys. The lesson is bigger than the fix.

The same file holds GN.room: create, join, pushState, start, watch. That is a full cross-device multiplayer layer, proven in production by Trouble, built on the same listener idea. Two phones watching one room document is two phones watching one drawer (Chapter 8), with turns as the data.
